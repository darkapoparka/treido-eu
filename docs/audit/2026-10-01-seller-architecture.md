## Decision and reasoning

Keep the existing Next.js modular application. Build the private seller workspace at `/app`, alongside buyer routes, using the same domain and selected Drizzle/PostgreSQL backend. Use next-forge as an architecture reference. Use Shopify admin as an operational UX reference. Neither migration supplies Treido's mixed personal/business ownership, publication/moderation, offers, concurrent stock allocation or independent payment purposes.

The decision favors continuity of the accepted frontend, a single authority for invariants, explicit SQL transactions and managed integrations with narrow adapters. It accepts that Treido must implement its marketplace domain and that several external providers require operating/configuration work. This is a project-specific engineering judgment, not an independently benchmarked claim that one stack is fastest or universally best.

## Alternatives and accepted tradeoffs

| Choice                                       | Why selected / why not                                                                                                      | Cost or revisit condition                                                                                      |
| -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| One modular Next app                         | Existing frontend and routes remain; server use cases also support later HTTP clients                                       | Separate a worker/service when measured runtime or independent deployment needs justify it                     |
| Drizzle + pg + Neon                          | Planned SQL constraints, explicit transactions, relational ownership and isolated test targets                              | Requires careful migrations/pool tests; an ORM is not an authorization system                                  |
| Clerk human sessions, local seller authority | One login can own personal inventory and belong to several businesses without a second tenant model                         | Auth costs and provider dependencies are qualified; do not synchronize two competing membership systems        |
| Inngest + transactional outbox               | Durable execution and per-function controls without building a complete scheduler; app DB bridges commit and event delivery | Adds a processor and operating cost; qualify data retention/regions/runtime and keep effects idempotent        |
| Vercel Node/Fluid + R2 + Resend + Sentry     | Defined hosting, media, mail and error ownership; add adapters only with consumers                                          | More vendors than an all-in-one stack; explicit project/environment/budget inventory is required               |
| Existing frontend state and visual system    | Preserves accepted buyer work and the actual form/category implementation                                                   | Admin tables/navigation are new bounded product UI and need responsive acceptance                              |
| Server-enforced tenancy before optional RLS  | One backend is the only DB caller; explicit ownership predicates, constraints and negative tests are inspectable            | Revisit RLS for another access path/defense requirement; never expose privileged direct-client database access |

## Architectural corrections carried into the owning docs

- Separate operation readiness from wizard progress, plan, seller type and verification. Personal drafting remains quick; business setup can resume across devices.
- Keep all creation/effects out of GET/render/prefetch. First-save/create commands are idempotent authenticated mutations.
- Authorize mutations under transaction locks so membership/restriction changes have a testable order relative to in-flight writes. Reauthorize stored private retry results.
- Bind media approval to immutable processing bytes, and jobs to durable effect identities. Executor acceptance and business completion are different states.
- Let accepted financial recovery run with service authority even when the initiating staff member is removed; discretionary imports still check current permission.
- Distinguish destination transfer from bank payout. A late webhook cannot block an already executed transfer; recovery may require refund/reversal.
- Deliver real draft/listing management before a complete merchant dashboard, with the full merchant integration test as a later explicit dependency of release.

The build order and failure tests are in the single queue. These corrections do not authorize implementation, provider provisioning, payments or release in this documentation task. The next ordinary build request can execute the ready policy slice without another architecture review.
