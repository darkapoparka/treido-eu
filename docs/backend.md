# Backend execution and security

Implement inside `app/apps/web`, not a new service fleet. Clerk session and `pg`/Drizzle adapters now back seller/draft, signup preference and resumable business setup use cases. Intended live Clerk/Neon bindings remain unqualified. [Marketplace](marketplace.md) owns invariants, [data model](data-model.md) owns the target schema/constraints, [API](api.md) owns boundary inputs/results and [billing](../billing.md) owns money policy. Other planned tables/commands remain specifications.

## Configuration foundation

`app/apps/web/src/server/config/backend-bindings.ts` validates explicit Clerk/Neon target metadata and credential shape. `backend-bindings.server.ts` is the `server-only` environment reader; invalid bindings throw a generic error with variable names/codes, never supplied values. [The web environment example](../app/apps/web/.env.example) contains empty provider bindings that intentionally fail validation. It is a template, not an active environment file, and does not change the guarded reference preview.

The contract requires application origin/region, deployment purpose, Clerk application ID and matching test/live key mode, and Neon project/branch/purpose/region/database/runtime role. Non-production uses test Clerk keys; production uses live keys. Preview/production origins must use HTTPS and cannot be loopback. A declared Vercel preview/production purpose must agree. Neon URLs require a TLS mode and must match the declared region, database and runtime role; privileged default roles and public secret aliases are rejected. Returned metadata excludes credentials and raw connection URLs.

This is local syntax and declaration validation. It does not verify that keys belong to the chosen Clerk application, that the endpoint belongs to the declared Neon project/branch, that a database role is actually least-privilege, or that a branch is isolated. The session and database adapters call this reader; a valid result never proves authentication, authorisation, connectivity or production readiness. T04a/T04b still require those checks against the intended resources. Storage provider/bucket and migration credentials remain separately qualified; no media or payment service is implied by this config.

The private `/app` routes implement seller selection, explicit personal/business creation, optional intent, recent drafts, revisioned item editing and resumable business setup. Server Actions verify Clerk again and run the current ownership/membership check inside the database transaction. `profile.manage` and `declaration.manage` protect their separate fields; declaration submission requests review and cannot approve itself. Saved-item review reads current fields, category policy, media, declaration, active usage and restriction facts. T39 adds a separate authenticated publish command; the review itself never writes or authorizes a publication. Withdrawal records a scoped immutable receipt and atomically removes public eligibility while retaining draft data and moderation. Operator declaration review, inventory, orders and billing remain separate consumers. Contact-only publication is implemented by T39 below. Private draft photos use the separate media boundary below; connected provider acceptance remains pending.

Participant commands implement ordered plain-text messages, owned attachment references and durable reporter receipts. They recheck the buyer/current seller inbox authority before reads, writes and replay. Opening contact requires current published/clear/eligible supply. `/ops` uses separate `reports.read` and `moderation.write` grants; a seller membership never grants operator access. Decisions persist reason, prior/new moderation state and revision with report review in the same transaction; affected sellers/reporters can submit immutable appeals. A narrow fixed-search-path function locks the requested current operator grant while runtime cannot grant itself authority. The web now provides separate buyer `/messages` and current-seller `/app/sellers/[sellerId]/inbox` views, reply/read/block actions, owned report receipts and affected-party appeal forms. Connected storage/session acceptance and public catalogue contact integration remain separate.

After qualifying the isolated development bindings, `pnpm dev:platform` starts the real adapter path at the configured loopback origin (template port 6419), with `.qa/treido-platform` output and reference mode disabled. `pnpm dev:web` remains the separate guarded reference preview. From `app/`, `pnpm --filter @treido/web db:migrate --check` inspects the declared migration/runtime target; `db:migrate --apply --branch <qualified-isolated-branch-id>` applies reviewed SQL using the separate direct migration connection. Its checksum receipt commits atomically with the schema, and repeat execution does not rerun applied SQL. The command supports development/test branches only and cannot prove provider ownership from declared IDs.

The development launcher validates the existing Clerk/Neon, private R2 and signed Inngest configuration contracts before spawning Next; its diagnostics contain variable names, never values. `pnpm dev:platform --background` detaches with file-backed output in `.qa/treido-platform-background/launcher.log`, preserves the reference preview and refuses an occupied port. The foreground command retains `.qa/treido-platform`. Both explicitly clear `MIGRATION_DATABASE_URL` in the child environment so Next cannot restore the migration credential from `.env.local`; migrations remain a separate command. A launched process and valid configuration shapes do not prove provider acceptance.

Signed Inngest Cloud cannot reach the loopback browser origin. Local development/test therefore requires a confirmed HTTPS `INNGEST_SERVE_ORIGIN` which advertises the callback only. Forward only `/api/inngest` through that reviewed development tunnel; do not expose the whole local development server. Keep `TREIDO_APP_ORIGIN` local for Clerk, application mutations and R2 CORS. Signature verification stays on with `INNGEST_DEV=false`; API/event-host and callback-path overrides remain rejected. Preview/production callbacks must match their configured application origin. This configuration does not create a tunnel, enroll an Inngest app or qualify any provider resources.

## Inbox and participant trust

The inbox is a server-authorized projection, not the device-local Studio preview. A null operating seller selects only conversations where the current human is the buyer; a concrete seller requires current inbox membership. A human who later joins the selling business cannot use their old buyer conversation to message themselves as seller. Read-only staff cannot reply or change contact settings.

The index uses 30-row cursor pages ordered by exact microsecond activity time and ID; cursor scope binds actor, seller, query and unread filter. Conversation pages load the most recent 50 messages, with bounded older pages. Read acknowledgements advance a per-human sequence monotonically and reject future positions. Visible foreground views refresh periodically; hidden/changed-account views cannot accept a late response from an old scope.

Contact preferences are per buyer/seller pair, not per listing. Independent buyer and seller block flags serialize with sends, and neither party can clear the other's flag. Commands require the current contact revision and a retry receipt. Plain-text sends retain their request key until acknowledged and cap new messages at 30 per minute per actor/pair. A successful message and its content-free notification intent commit together; this implements inbox unread state, not delivered external mail or push. Attachment persistence remains in the existing participant boundary; these new screens do not expose an unimplemented upload/download control.

Report lists/details belong to their reporter. Listing decision history requires current seller listing access and omits reporter/operator identities. Appeal receipts are immutable and do not lift restrictions. The new routes remain explicitly unavailable without the real backend configuration; no reference-data fallback is introduced.

## Accepted publication and public product delivery

T39 connects saved draft, processed photos, contact-only publication, public product detail/gallery, existing durable buyer contact and withdrawal. The additive `0011_listing_publications.sql` migration stores immutable accepted draft/term/photo snapshots. A publish request contains the expected draft revision, the exact ordered photo ID/revision set, handover details and explicit ownership/accuracy/photo-rights acknowledgements. Personal sellers also affirm a personal rather than business sale. Business publication requires the latest accepted declaration; neither a paid plan nor submission approves one.

The command locks current seller authority, Free-plan usage, the listing, current policy and photos. It checks current leaf rules, mandatory fields, declaration status, processed bytes and the last active slot before committing one publication. A scoped retry key returns the same currently live acceptance, not another publication. After withdrawal or replacement it cannot revive an old version. Pending category rules remain pending; no policy or declaration approval is fabricated by the application or migration.

Live records use `/products/[id]` outside explicit reference mode. The public query, gallery delivery, new conversations, message reply eligibility and listing reports use the same accepted-publication predicate. Public photos use versioned URLs, bounded object reads, checksum verification, eligibility checks before and after storage I/O and `private, no-store`. Withdrawal, removal, changed media, stale category rules, restricted sellers and superseded declarations deny subsequent reads. Private object keys, declaration contact data and human provider IDs never enter the public view.

Published items open review/withdraw controls rather than an editor that cannot save. Withdraw, edit the retained draft/photos, then explicitly republish; accepted snapshots do not change. Historical inbox captions use the accepted listing instead of leaking later private draft edits. This phase is contact-only: no checkout button, payment collection, shipping guarantee or invented stock claim. Public search/storefront projections and actual development Clerk/Neon/R2/Inngest qualification are still separate tasks.

## One use case, explicit authority

Each entry point follows this sequence: authenticate → validate bounded input → authorize actor/resource/current seller membership → execute an atomic command or bounded query → return a minimal result. The use case rechecks the relevant state; an authenticated layout or hidden button is not sufficient.

Map Clerk's stable subject to a local `User` using a unique constraint/idempotent creation. Keep private identity separate from public seller profiles. Use the SDK's verified server session, not a browser user ID. Clerk does not become authority for a second conflicting seller/plan model. Current app-owned membership and restrictions decide seller operations. [Clerk server auth](https://clerk.com/docs/reference/nextjs/app-router/auth) and [Next data security](https://nextjs.org/docs/app/guides/data-security) are implementation references.

Example contract shape, not an existing API:

```ts
type CommandResult<T> =
  | { ok: true; data: T; revision?: number }
  | { ok: false; code: 'UNAUTHENTICATED' | 'INVALID_INPUT' | 'FORBIDDEN' |
      'NOT_FOUND' | 'CONFLICT' | 'QUOTA_EXCEEDED' | 'RATE_LIMITED' |
      'NOT_AVAILABLE' | 'PENDING'; fieldErrors?: Record<string, string[]> };
// The server derives Actor from the verified session, never from browser input.
// publishListing(actor, { sellerId, draftId, expectedRevision, requestId })
```

Use names and error codes consistently; avoid a universal command bus. Separate authentication failure from validation/conflict according to the transport. Do not leak foreign resource existence or raw database/provider errors. Correlate internal diagnostics with a non-secret request ID.

## Database boundary

Server database modules import `server-only`. Use parameterized Drizzle/SQL, select explicit columns, apply seller/actor predicates and bound results. Never expose the database directly to the browser or ship privileged credentials. Use a least-privilege runtime role; migrations use a separate privileged path. RLS may provide defense in depth, but is not automatically present because PostgreSQL is used. Test actual runtime access and any adopted RLS context.

For transactions acquire one connection and release it in `finally`; every statement and lock in that transaction uses the same client. Bound pool size/timeouts according to hosting concurrency and the database budget. Co-locate application/database regions and measure round trips. Avoid session-scoped assumptions behind a transaction pooler. See [Drizzle transactions](https://orm.drizzle.team/docs/transactions) and [Neon latency/pooling guidance](https://neon.com/blog/how-to-minimise-the-impact-of-database-latency).

Use a reusable bounded `pg` pool for the selected Node/Fluid host and the supported pool lifecycle integration (`attachDatabasePool` when qualified on Vercel). The application pool limits per-instance acquisition; the selected Neon pooled endpoint has its own backend connection budget. Test both rather than multiplying an unlimited pool across instances. Use a direct endpoint and separate migration role for migrations. Configure acquisition/statement/idle-transaction timeouts and verify rollback/release on failures. Never combine `BEGIN` and later statements through unrelated `pool.query` calls. [Neon's connection guide](https://neon.com/docs/guides/vercel-connection-methods) and [pg transactions](https://node-postgres.com/features/transactions) support this driver choice; actual pool limits are qualified in T04b.

Initial isolation uses explicit seller predicates and database ownership constraints; no browser Data API and no implicit RLS promise. Use `(seller_id, resource_id)` references where a child could otherwise cross tenants. T04b must prove the runtime role cannot perform schema/role administration and that each repository query applies the intended scope. If RLS is later added, use a separately reviewed migration and test pooled transaction-local identity, workers and public projections.

Use foreign keys, uniqueness, check constraints and appropriate indexes for invariants. Optimistic revisions protect ordinary edits; transactions/locks protect final-slot quotas and allocation. Use a consistent resource lock order. Do not read a count and increment later in another request. Retry serialization/deadlock failures only with bounded attempts and replay-safe commands.

Permission checks for a mutation participate in its transaction. Adopt a documented lock order: seller/authority rows, membership, usage rows, listing/SKU IDs in sorted order, then the operation's order/payment rows. Authorized mutations hold suitable shared authority/membership locks until commit; revocation/restriction changes take conflicting locks in the same order. Do not use a pre-transaction role check that can race with revocation. The acceptance boundary is ordering: a command that won authorization/locks before revocation may finish; after revocation commits, subsequent commands/reads are denied. Already delivered data is not recallable. Last-owner and invitation changes additionally serialize on the seller's membership set.

Multi-line checkout/accepted offers use the same inventory use case: lock sorted listing/SKU IDs, verify current state, reserve all lines and persist the immutable quote/attempt in one transaction. Unique quantity-one and stocked SKUs have distinct constraints. Imports and seller stock edits cannot bypass active holds, expected revisions, leaf rules or entitlement counters. Every refund checks remaining refundable line/amount quantities atomically.

Add reviewed, versioned migrations and development seeds with synthetic data. No schema push to shared/production databases from an agent session. Test migrations on an isolated branch/database and from the previous supported schema. Prefer expand/backfill/contract for live compatibility; a down migration is not guaranteed safe for data or external money.

## Idempotency and durable effects

A retry key is scoped to actor, operation and resource; store an input hash and result/state. Same key with different input conflicts. Concurrent requests claim one operation atomically. Recheck current access before returning a stored private result to a retrier. Financial retry retention must cover plausible delayed provider outcomes; do not choose an arbitrary short expiry.

Write a domain change and required outbox intent in the same transaction. Invoke external providers after commit using a stable operation key. D29 selects Inngest at the first durable consumer (T04f), with a narrow PostgreSQL dispatcher rather than a home-built workflow system. Duplicate delivery remains possible; consumers deduplicate. Do not install an additional queue/workflow engine alongside it.

The dispatcher leases a bounded batch with reclaimable expiry, publishes a stable job/event ID, and records handoff only after durable executor acceptance. A best-effort post-commit wake-up reduces latency; an authenticated scheduled sweep repairs a crash before dispatch. Never rely on a browser request, `after()` or a fire-and-forget promise as the only delivery mechanism. Provider handoff and domain-effect completion are different fields. A sweeper finds dispatched-but-stalled jobs as well as unsubmitted rows; reconciling the durable effect determines whether to redrive. Lease expiry is not proof that an external effect failed.

Inngest functions execute bounded steps in the existing Node app, with a global concurrency budget plus per-seller/provider limits. Events contain opaque IDs, event/schema version and correlation, not raw addresses, messages, bank details or signed URLs. Step inputs/results also enter executor history: return small IDs/statuses and keep secrets/private payloads inside the executing step. Verify signed executor requests and exact environment/app identity; isolate development/test events and credentials. Configure retries, terminal failure alerts, expiry/retention and function-version compatibility before exposing a consumer.

Feature handlers reload authoritative state and claim one durable effect before execution. A crash after a successful provider call but before recording its result retries with the same provider key or reconciles the known provider object. Provider deduplication windows may expire; never blindly resend an old unknown charge/email under a new key. For user-discretionary work (imports, new notifications, draft media), recheck current membership/policy/consent. Service work for accepted obligations (payment reconciliation, refund, allocation cleanup) uses a narrowly authorized service actor and persists through staff revocation; no staff session token is stored in a job.

T04f tests commit-before-dispatch crash, accepted-event-before-local-ack crash, duplicate/reordered delivery, provider-success-before-local-result crash, expired lease, removed member, service recovery after removal and dead-letter redrive. Inngest's execution history does not replace PostgreSQL's financial ledger, moderation history or operator audit. [Durable execution](https://www.inngest.com/docs/durable-execution/durable-workflows) explains step retries; it does not make arbitrary external effects exactly-once.

For webhooks verify signature over the required raw bytes before trusting payload. Correlate provider/account/mode/object; store/deduplicate authenticated receipt durably, then acknowledge and process with retries. Acknowledge only according to the provider contract. Out-of-order events cannot undo terminal state. See [Stripe webhooks](https://docs.stripe.com/webhooks).

## Uploads and user content

The local T04f implementation uses reviewed `0003_durable_jobs.sql`: a domain transaction enqueues the job and its stable effect identity together. Dispatch claims immediately before each bounded handoff; expired and accepted-but-stalled work is reclaimable. The signed Inngest adapter registers `durable-job-v1` and a once-per-minute `outbox-repair-v1` sweep. An independent bearer-protected repair endpoint permits manual recovery; a distinct repair credential and expected generation are required for audited dead-letter redrive. Member work rechecks current authority when claimed, before applying the result and before replay acknowledgement. Consumer resource locks precede job/effect completion locks. An executor receipt is never domain completion. Intended provider binding and live callback/scheduler qualification remain pending.

Authorize an upload intent for the current owner, assign an opaque object key, and enforce size/count/type limits. Validate actual file bytes/dimensions, not the browser MIME type; strip unnecessary metadata, scan/reject unsafe content, and process in private staging. Ready state is server-owned. Attach only owned, ready assets; unbound uploads expire through a scoped cleanup task.

Selected storage is R2 via the S3 API. Bind the intended private bucket/jurisdiction and exact allowed upload origin in T06b. A presigned PUT is temporary bearer access, not proof of valid bytes or current ownership. Freeze the uploaded object version/checksum before processing so reusing an upload URL cannot replace already-approved media. Re-encode supported raster photos with bounded Sharp processing; keep originals/quarantine private and publish only approved derivatives through an eligibility-checked delivery route. Check content length and decoded pixel limits before expensive work; stale/foreign upload completion and partial processing cannot become ready media.

The draft editor now supports up to 12 private JPEG/PNG/WebP photos, each at most 12 MiB and 40 million decoded pixels. Intent creation serializes the last photo slot on the owned draft. A five-minute PUT signs length/type; completion copies the matching source ETag to a fresh immutable private key, then atomically persists processing state and the outbox intent. The worker verifies the original SHA-256, rejects unsupported/animated formats, strips metadata and re-encodes at a maximum 1600-pixel edge. Only its completed transaction exposes a ready derivative. Delivery checks current seller/draft access before and after storage I/O and verifies the derivative checksum; it is private and uncached. Reorder/remove commands require every current asset revision, and removal cancels pending processing. Failed uploads preserve draft fields; their same-page retry retains the same intent. A reopened page resumes server processing/staged completion, while an unuploaded local file must be chosen again. Publication/moderation approval, scoped expiry/orphan cleanup and live R2/CORS qualification are still outstanding; this draft path grants no public media eligibility.

Use plain text or a narrowly sanitized rich-text format; never render arbitrary seller HTML. Validate external links and disallow arbitrary server-side URL fetches that could reach internal services. Private attachments require current participant authorization. Delivery URLs are short-lived/revocable where appropriate; do not make private buckets public to fix a preview.

## Abuse, jobs and operating controls

Set server-enforced limits for signup, publish, upload, messaging, offers, search and AI. Use shared durable counters where multiple instances must agree; client timers and per-process maps are not production abuse limits. Validate request size and pagination. Protect job/admin endpoints with explicit service/operator credentials; deny default access.

Log actor/resource IDs, operation, duration, outcome and correlation—not secrets, tokens, full contact details, messages or payment payloads. High-risk changes create restricted audit records. Recoverability matters: report failed jobs, stale reservations and reconciliation queues to an operator rather than silently dropping effects.

Before calling a slice integrated, test two real users/two businesses against isolated persistence, removed memberships, foreign IDs, stale revisions, concurrent final-slot operations, replay and provider failure. Unit fixtures alone do not establish authorization or database correctness.
